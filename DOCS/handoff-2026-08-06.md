### Bug found and root-caused: "Leads tab bounces back to Setup"
This had been flagged unreproducible across *two* prior sessions. Root cause this time: **not an app bug** — **VS Code's Live Preview extension** has its own server quietly squatting on `127.0.0.1:3000` (confirmed via its injected `___vscode_livepreview_injected_script` and a `ws://127.0.0.1:3001/...` reload socket) and auto-reloads any tab pointed at that port whenever `index.html` changes on disk — which happens constantly while editing, and could also fire from this Drive-synced folder's background sync touching file mtimes. The reload resets the SPA to its default tab, which looks exactly like "Leads → Setup." **Practical fix: don't test this app via VS Code's "Open with Live Preview" — use a plain static server or the deployed GitHub Pages URL.** This session used `python -m http.server 3050` (not 3000) for all testing to sidestep the conflict.

While chasing that, a **real bug was found and fixed**: the Settings modal opened with a completely blank panel (no tab content, nothing visibly selected). Cause: `activateSubtab()` used an unscoped `document.querySelectorAll(".subtab-panel")`/`.subtabs button` selector; the new Settings modal reuses those same class names for its own LLM APIs/Usage/Backend sub-tabs, so `activateSubtab()`'s one-time call at page load (`initTabs()`) was stripping "active" off the Settings modal's panels too. Fixed by scoping to `#tab-setup .subtabs button`/`#tab-setup .subtab-panel`.

A second real bug found via user screenshot: on a fresh/empty profile, step 2 ("Extract profile") and step 3 ("Review, tag & save") rendered as **done/active** (filled/ringed orange) instead of locked. Cause: `loadSavedProfile()` checked `if (profile.extracted)` — the backend always returns a non-null `extracted` object once any profile row exists, even one where every field is empty, so the truthiness check always passed. Fixed to require actual content (`skills.length || industries.length || keywords.length || summary.trim()`).

### Round 3 — button placement, per-subtab Save/Load, alignment/visual fixes
- **Save/Load profile buttons moved** from inside step 3 to a shared row at the top-right of `#tab-setup`, under the subtabs nav, visible on **all three subtabs** (`.save-scope-row` is now `display:flex; justify-content:space-between`, the old border-bottom removed — that was the "sliver/double-line" the user pointed at).
- **Save is now genuinely per-subtab**, not just visually shared — this was an explicit user question/request. `activeSetupSubtab()` (top-level helper) + `updateProfileIoUI()` dispatch the Save/Load buttons' behavior, label, tooltip, and default filename based on which subtab is active:
  - **My Profile** → `my-profile.json` (resume_text + extracted tags + manual_tags) — Save stays disabled until there's actual content (resume text or ≥1 tag).
  - **Search Criteria Filters** → `search-criteria-filters.json` (active_ats/contract_modes/industries only — no companies, no countries). Load re-renders via the now-**top-level** `renderAtsContractIndustries()` (hoisted out of `initScope()`'s closure specifically so this handler could call it) and autosaves.
  - **Location Filters** → `location-filters.json` (countries only). Load calls `setSelectedCountries()` and autosaves.
  - Save is always enabled on the Criteria/Locations subtabs (no meaningful "empty" state there).
- **Buttons changed from pill/capsule shape to rectangles** (`border-radius: 999px` → `4px` on `.compact-btn`) — user's rule: capsules are for tags only, action buttons should look like every other rectangular button in the app. This also affects the Saved Searches "Apply" button and "Save current search" button, which reuse `.compact-btn`.
- **Extract-progress-status text repositioned** to sit directly under the progress bar (was appearing under the button instead). `.extract-row` changed from flex to a 2-row CSS grid (`grid-template-columns: auto 1fr`) — button+icon and the track share row 1 (vertically centered together), the status text is pinned to column 2 on row 2. Verified pixel-exact via `getBoundingClientRect()` (careful: don't name a test variable `status` at the top level of a `javascript_exec` eval — it collides with `window.status` and silently drops values).
- **"Update" button added** next to the step-3 "Review, tag & save" heading. Click → `saveProfileNow()` immediately + marks step 3's circle solid (`step-done`) via a new `profileUpdated` flag (persists true across repeat clicks, never auto-resets — matches the user's literal spec).
- **Sticky-header "sliver" fixed**: `initStickyHeader()`'s height measurement used `header.offsetHeight` (rounds to whole px), leaving a sub-pixel gap between the sticky app-header and the sticky subtabs bar that let scrolled content peek through. Changed to `Math.ceil(header.getBoundingClientRect().height)` (fractional, always overlaps rather than gaps).
